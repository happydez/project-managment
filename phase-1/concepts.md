# Фаза 1. Пункт 1. Концепции проекта

Задание: придумать не менее 4 концепций программного проекта.

Требования к концепции:

- проект компактный: от 10 до 15 use cases (или MVP такого размера);
- с выбранной концепцией дальше нужно будет описать use cases с альтернативными и негативными сценариями, оценить проект в COSMIC FP и Use Case Points, оценить трудозатраты экспертно, разбить реализацию на 20-25 задач с ресурсами разных специальностей и связями предшествования и составить календарный план.

Все концепции относятся к одной области - внутренним инструментам для DevOps и эксплуатации. Для каждой концепции приведён предварительный список use cases, чтобы проверить, что она укладывается в нужный размер. Подробно use cases будут расписаны в фазе 3 только для выбранной концепции.

## A1. Сервис управления системными службами серверов

Сервис для централизованного управления службами systemd на группе Linux-серверов. На каждом сервере работает агент, который сам подключается к управляющему узлу по защищённому соединению. Через веб-панель или API можно посмотреть состояние служб и выполнить над ними действие: запустить, остановить, перезапустить, перечитать конфигурацию, включить или отключить автозапуск. Что именно разрешено пользователю, задаётся политиками доступа (сервер, служба, действие). Все действия записываются в журнал аудита.

Акторы: администратор, оператор (пользователь с ограниченными правами), система автоматизации (CI, бот) через API, агент на сервере.

Предварительный список use cases:

1. Вход в панель управления.
2. Подключение сервера к управляющему узлу по одноразовому токену.
3. Просмотр списка серверов и их служб.
4. Просмотр состояния службы.
5. Выполнение действия над службой (start, stop, restart, reload, enable, disable).
6. Создание и блокировка пользователя.
7. Создание политики доступа (сервер, служба, действие).
8. Назначение политики пользователю.
9. Выпуск и отзыв API-токена для системы автоматизации.
10. Выполнение действия над службой через API по токену.
11. Просмотр журнала аудита с фильтрами.
12. Автоматическое продление сертификата агента.

Особенности: распределённая схема (управляющий узел и агенты), проверка прав на каждое действие, защищённое соединение с агентами, много негативных сценариев (нет прав, служба не найдена, агент недоступен, команда завершилась ошибкой).

## A2. Мониторинг доступности сервисов со статус-страницей

Сервис периодически проверяет доступность сайтов и API команды (HTTP-ответ, время ответа, срок действия SSL-сертификата), при сбое открывает инцидент и оповещает инженеров. Для пользователей есть публичная статус-страница, на которой видно текущее состояние сервисов и история инцидентов.

Акторы: инженер, внешний пользователь (читает статус-страницу), проверяемый сервис, почтовый сервис, Telegram.

Предварительный список use cases:

1. Вход в систему.
2. Добавление и настройка проверки (адрес, интервал, ожидаемый ответ).
3. Выполнение проверки по расписанию.
4. Автоматическое открытие инцидента при серии неудачных проверок.
5. Оповещение инженеров по почте и в Telegram.
6. Ручное обновление статуса инцидента и публикация комментария.
7. Закрытие инцидента.
8. Предупреждение об истечении SSL-сертификата.
9. Планирование технических работ с отображением на статус-странице.
10. Просмотр публичной статус-страницы.
11. Подписка внешнего пользователя на обновления статуса.
12. Отчёт о доступности (uptime) за период.

Особенности: фоновые задачи по расписанию, публичная и закрытая части, два канала оповещений, есть работа для дизайнера (статус-страница).

## A3. Сервис контроля резервного копирования

Сервис следит за тем, чтобы резервные копии серверов и баз данных действительно делались и из них можно было восстановиться. Агент на сервере после каждого бэкапа сообщает результат: время, размер, контрольную сумму. Если бэкап не пришёл вовремя, завершился ошибкой или подозрительно уменьшился в размере, ответственный получает оповещение. Также сервис планирует регулярные тестовые восстановления и хранит их результаты.

Акторы: администратор, ответственный за систему, агент резервного копирования на сервере, почтовый сервис.

Предварительный список use cases:

1. Вход в систему.
2. Регистрация сервера или базы данных и выдача токена агенту.
3. Настройка политики бэкапа (расписание, срок хранения, допустимое отклонение размера).
4. Приём отчёта о бэкапе от агента.
5. Обнаружение пропущенного бэкапа по расписанию.
6. Обнаружение аномалии (ошибка, резкое изменение размера, неверная контрольная сумма).
7. Оповещение ответственного по почте.
8. Назначение тестового восстановления.
9. Отметка результата тестового восстановления.
10. Просмотр состояния всех систем на общей панели.
11. Просмотр истории бэкапов системы.
12. Отчёт о соблюдении политик резервного копирования за период.

Особенности: несколько источников данных (агенты) и проверки по расписанию, логика обнаружения аномалий простая, есть работа для дизайнера (общая панель), внешняя зависимость только почтовый сервис.

## A4. Telegram-бот оповещений о критических событиях аудита

Сервис принимает события из журналов аудита серверов и приложений (вход под root, изменение прав, отключение аудита, неудачные попытки входа подряд и т. п.), проверяет их по правилам и отправляет оповещения дежурным в Telegram. Дежурный может подтвердить оповещение прямо в боте, а если никто не отреагировал за заданное время, оповещение эскалируется следующему человеку.

Акторы: администратор сервиса, дежурный инженер, источник логов (агент или webhook), Telegram.

Предварительный список use cases:

1. Регистрация источника логов и выдача ему токена.
2. Приём события аудита от источника.
3. Создание и редактирование правила оповещения (условие, уровень критичности).
4. Отправка оповещения в Telegram при срабатывании правила.
5. Подтверждение оповещения дежурным из бота.
6. Эскалация неподтверждённого оповещения.
7. Ведение графика дежурств.
8. Подписка на оповещения по проекту или уровню критичности.
9. Временное отключение правила (режим обслуживания).
10. Группировка повторяющихся событий в одно оповещение.
11. Просмотр истории оповещений с фильтрами.
12. Отчёт по количеству оповещений и времени реакции дежурных.

Особенности: поток входящих событий и проверка правил, работа с таймерами для эскалации, интерфейс дежурного ограничен ботом, зависимость от Telegram Bot API.
