# Фаза 3. Пункт 4. Коллективная экспертная оценка

Задание: оценить проект коллективным экспертным путём. Оценить трудозатраты каждого use case или более мелких элементов с достижением согласованности относительно итоговой оценки, затем агрегировать эти оценки в оценку всего проекта.

Оценки и расчёты - в книге [project-estimation.xlsx](project-estimation.xlsx), лист «Экспертная оценка». Ниже те же данные в виде таблиц.

## Что оценивали

Оценивались 12 use cases из [use-cases.md](use-cases.md) целиком, без разбиения на более мелкие элементы. Так экспертную оценку можно построчно сравнить с оценками в COSMIC и Use Case Points.

К use cases добавлен тринадцатый элемент - общие работы, которые не относятся ни к одному use case, но без которых проект не сделать:

- каркас проекта и структура базы данных;
- защищённый канал связи между управляющим узлом и агентом;
- сборка, развёртывание и установочный пакет агента;
- сквозное тестирование на стенде с несколькими серверами.

Единица оценки - человеко-день (8 часов). В оценку элемента входят проектирование, программирование всех его частей (панель, API, управляющий узел, агент) и модульные тесты. Не входят анализ требований, системное и приёмочное тестирование, исправление найденных в них дефектов, управление проектом и ввод в эксплуатацию.

## Метод

Использован покер планирования. Экспертами были все четыре участника команды.

1. Команда коротко обсуждает, что входит в элемент.
2. Каждый эксперт выбирает карту из набора 1, 2, 3, 5, 8, 13, 20, 40 человеко-дней, не показывая её остальным.
3. Карты открываются одновременно.
4. Оценки считаются согласованными, если наименьшая и наибольшая карты совпадают или стоят в наборе рядом (например, 5 и 8). Тогда итогом становится карта большинства.
5. Если карты расходятся сильнее, авторы наименьшей и наибольшей оценок объясняют их, команда обсуждает расхождение и голосует ещё раз.

Шаг между картами растёт вместе с оценкой: чем больше элемент, тем грубее его можно оценить, и спорить о разнице в один день для двухнедельной работы нет смысла. Одновременное открытие карт не даёт участникам подстраиваться под чужое мнение.

## Агрегация в оценку проекта

Элементы не пересекаются и вместе покрывают всю разработку, поэтому оценка проекта равна сумме оценок элементов.

| Показатель | Значение |
|------------|----------|
| Use cases | 73 чел.-дня |
| Общие работы | 20 чел.-дней |
| Итого | 93 чел.-дня |
| | 744 чел.-ч (по 8 ч) |
| | 4.7 чел.-месяца (по 160 ч) |

Разброс мнений в первом раунде показывает неопределённость оценки. Если по каждому элементу взять наименьшую карту первого раунда, получится 59 чел.-дней, если наибольшую - 118. Итоговые 93 чел.-дня лежат ближе к верхней границе: при обсуждении чаще выяснялось, что в оценке что-то не учли, чем что учли лишнее.

## Анализ

- Самые трудоёмкие use cases - подключение сервера (UC2) и действие над службой (UC5), по 13 чел.-дней. В обоих участвуют и управляющий узел, и агент, и systemd, и в обоих много негативных сценариев.
- Общие работы - самый большой элемент, 21.5% оценки. Это та часть проекта, которой в use cases не видно.
- Use cases про учётные записи и права (UC1, UC6, UC8, UC9) оценены в 2-3 чел.-дня каждый: это обычные формы и операции с базой данных без обращения к агенту.
- Оценка охватывает только проектирование, программирование и модульные тесты. Чтобы сравнивать её с оценкой в Use Case Points, которая включает весь цикл разработки, её нужно достроить. Это сделано в [выводах по фазе](conclusions.md).
