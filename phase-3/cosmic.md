# Фаза 3. Пункт 2. Оценка в COSMIC Function Points

Задание: оценить проект в COSMIC Function Points.

Измеряется проект A1 «Сервис управления системными службами серверов» по use cases из [use-cases.md](use-cases.md). Измерение выполнено в книге [project-estimation.xlsx](project-estimation.xlsx), лист «COSMIC». Ниже те же данные в виде таблиц.

## Метод

COSMIC (ISO/IEC 19761) измеряет функциональный размер программы, то есть объём того, что она делает для своих пользователей, независимо от языка и технологий. Единица измерения - CFP (COSMIC Function Point).

Работа программы рассматривается как набор функциональных процессов. Функциональный процесс запускается событием во внешнем мире и состоит из перемещений групп данных. Видов перемещений четыре:

| Вид | Обозначение | Откуда и куда |
|-----|-------------|---------------|
| Entry | E | от функционального пользователя в систему |
| Exit | X | из системы функциональному пользователю |
| Read | R | из постоянного хранилища в систему |
| Write | W | из системы в постоянное хранилище |

Каждое перемещение одной группы данных даёт 1 CFP. Размер процесса равен числу его перемещений, размер проекта - сумме размеров всех процессов.

## Стратегия измерения

| Параметр | Значение |
|----------|----------|
| Цель | получить размер проекта, чтобы сравнить его с оценками в Use Case Points и экспертной оценкой |
| Область | весь сервис целиком: управляющий узел и агент измеряются как одна программа |
| Источник требований | 12 use cases с альтернативными сценариями |
| Уровень детализации | функциональные процессы и перемещения групп данных |

Функциональные пользователи - те, кто отправляет данные в систему или получает их из неё. Это акторы из [use-cases.md](use-cases.md):

| Функциональный пользователь | Что передаёт системе | Что получает от системы |
|-----------------------------|----------------------|-------------------------|
| Администратор, Оператор | запросы и данные через веб-панель | списки, карточки, результаты, сообщения |
| Система автоматизации | запросы API | ответы API |
| systemd | состояние служб, результаты команд, строки журнала | запросы состояния и команды |
| Таймер | сигнал времени | ничего |

Так как сервис измеряется целиком, обмен между управляющим узлом и агентом происходит внутри границы системы и в размер не входит. Обмен агента с systemd пересекает границу и считается.

## Группы данных

Группа данных описывает один объект, о котором система хранит или передаёт данные.

| Группа данных | Что описывает | Хранится |
|---------------|---------------|----------|
| Пользователь | учётная запись: логин, имя, роль, статус, пароль | да |
| Сессия | вход пользователя в панель | да |
| Политика | название и правила (сервер, служба, действия) | да |
| Назначение политики | связь политики с пользователем или API-токеном | да |
| Сервер | имя, статус, время последней связи | да |
| Служба | имя, состояние, автозапуск | да |
| Токен подключения | одноразовый токен для подключения сервера | да |
| Сертификат агента | сертификат, срок действия, признак отзыва | да |
| API-токен | название, хэш, срок, время последнего использования | да |
| Действие над службой | запрос действия от пользователя и его результат | нет |
| Обмен с systemd | команда или запрос к systemd и ответ на него | нет |
| Журнал службы | строки журнала службы из systemd | нет |
| Запись аудита | кто, что, над чем и с каким результатом сделал | да |
| Сигнал времени | срабатывание расписания | нет |
| Сообщение | сообщение об ошибке или подтверждение | нет |

## Правила подсчёта

- Функциональный процесс соответствует основному сценарию use case или его альтернативному сценарию, если тот запускается отдельным событием (например, блокировка пользователя или отзыв токена). Альтернативные сценарии, которые отличаются только условием внутри процесса, отдельными процессами не считаются.
- Негативные сценарии не образуют отдельных процессов. Все сообщения об ошибках и подтверждения процесса считаются одним Exit группы «Сообщение», как рекомендует метод.
- Одно и то же перемещение одной группы данных считается в процессе один раз, даже если выполняется несколько раз. Поэтому запись начала и результата операции в журнал аудита - один Write, а действие над несколькими службами не больше действия над одной.
- Проверка прав по политикам даёт два Read: назначения политик и сами политики.
- Проверка действующей сессии в каждом процессе панели отдельно не считается: это общая техническая функция, а не требование конкретного use case.
- Запрос списка или карточки считается как Entry той группы данных, которую запрашивают.

## Результат

Функциональный размер проекта - 215 CFP: 32 функциональных процесса, в среднем 6.7 CFP на процесс, от 3 до 13.

Что видно из измерения:

- Размер распределён по use cases довольно ровно, от 5% до 12%. Нет одного use case, который определял бы размер проекта.
- Самые большие use cases - UC10 (действие через API, 25 CFP), UC9 (API-токены, 24), UC2 (подключение сервера, 23) и UC7 (политики, 23). На действия над службами и работу с API (UC5, UC9, UC10) приходится 70 CFP, треть проекта.
- Самые большие процессы - те, где система проверяет права, обращается к systemd и пишет аудит: действие через API (13), просмотр состояния службы (12), запрос состояния через API (12), действие над службой (11).
- По видам перемещений: Read - 61, Exit - 57, Write - 57, Entry - 40. Read и Write вместе дают 55% размера, то есть система в основном работает с хранимыми данными.
- Чаще всего перемещается «Запись аудита» - 34 перемещения, 16% размера: аудит затрагивает 26 процессов из 32. Далее идут «Политика» (26) и «Сообщение» (24). Проверка прав и аудит - сквозные функции, которые присутствуют почти везде.
- На обмен с systemd приходится 17 перемещений (группы «Обмен с systemd» и «Журнал службы»), 8% размера.

## Ограничения измерения

- COSMIC измеряет только функциональный размер. Нефункциональные требования (защищённое соединение, шифрование, производительность) и сложность алгоритмов в него не входят.
- Сервис измерен как одна программа, поэтому обмен между управляющим узлом и агентом в размер не вошёл, хотя его нужно разработать. Работа агента учтена только там, где он обращается к systemd. Это нужно иметь в виду при сравнении с другими оценками: размер в CFP скорее занижает объём работ по агенту.
- Переводить CFP в трудозатраты можно только через производительность (часов на 1 CFP), а у команды такой статистики нет. Поэтому здесь приводится только размер, а соотношение с трудозатратами получено в выводах по фазе из сравнения с оценкой в Use Case Points и экспертной оценкой.
