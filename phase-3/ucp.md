# Фаза 3. Пункт 3. Оценка в Use Case Points

Задание: оценить проект в Use Case Points и прикинуть трудозатраты на их основе.

Оценивается проект A1 «Сервис управления системными службами серверов» по use cases из [use-cases.md](use-cases.md). Расчёт выполнен в книге [project-estimation.xlsx](project-estimation.xlsx), лист «UCP». Ниже те же данные в виде таблиц.

## Метод

Метод Use Case Points (Г. Карнер, 1993) оценивает размер проекта по его акторам и use cases, а затем поправляет его на технические требования и на условия, в которых работает команда:

```
UCP = (UAW + UUCW) × TCF × ECF
```

| Величина | Что это |
|----------|---------|
| UAW | вес акторов: чем сложнее способ взаимодействия актора с системой, тем больше вес |
| UUCW | вес use cases: чем больше в use case транзакций, тем больше вес |
| UUCP | невыровненные UCP: UAW + UUCW |
| TCF | поправка на технические факторы (13 факторов) |
| ECF | поправка на факторы среды, то есть на команду и условия работы (8 факторов) |

Трудозатраты получаются умножением UCP на число часов на один UCP.

В отличие от COSMIC, метод сразу учитывает нефункциональные требования и опыт команды и доводит оценку до часов.

## 3. Технические факторы (TCF)

Каждый фактор оценивается от 0 (не имеет значения для проекта) до 5 (очень важен). Оценки поставлены командой совместно.

| № | Фактор | Вес | Оценка | Вес × оценка | Обоснование |
|---|--------|-----|--------|--------------|-------------|
| T1 | Распределённая система | 2 | 4 | 8 | управляющий узел и агенты на серверах |
| T2 | Требования к времени отклика | 1 | 3 | 3 | состояние службы и результат действия нужны за секунды |
| T3 | Эффективность работы пользователя | 1 | 3 | 3 | обычная панель управления |
| T4 | Сложная внутренняя обработка | 1 | 2 | 2 | сложных алгоритмов нет, только проверка прав по политикам |
| T5 | Повторное использование кода | 1 | 2 | 2 | общий код проверки прав для панели и API |
| T6 | Простота установки | 0.5 | 4 | 2 | агент должен ставиться одной командой |
| T7 | Простота использования | 0.5 | 3 | 1.5 | пользователи - технические специалисты |
| T8 | Переносимость | 2 | 2 | 4 | агент должен работать на разных дистрибутивах Linux |
| T9 | Простота внесения изменений | 1 | 3 | 3 | обычные требования к сопровождению |
| T10 | Параллельная обработка | 1 | 3 | 3 | много агентов и одновременные действия |
| T11 | Особые требования безопасности | 1 | 5 | 5 | сертификаты, токены, политики, аудит - основа сервиса |
| T12 | Доступ для сторонних систем | 1 | 4 | 4 | API для систем автоматизации |
| T13 | Специальное обучение пользователей | 1 | 1 | 1 | обучение не требуется |
| | Сумма | | | 41.5 | |

TCF = 0.6 + 0.01 × 41.5 = 1.015.

Технические требования почти не меняют оценку: проект с точки зрения метода средний. Высокие оценки за распределённость и безопасность уравновешены низкими за сложность обработки и обучение пользователей.

## 4. Факторы среды (ECF)

Оценки от 0 до 5. Для E1-E6 высокая оценка уменьшает трудозатраты, для E7-E8 (вес отрицательный) увеличивает. Оценки поставлены для команды с опытом, как у нас, но работающей над проектом полный рабочий день.

| № | Фактор | Вес | Оценка | Вес × оценка | Обоснование |
|---|--------|-----|--------|--------------|-------------|
| E1 | Знакомство с процессом разработки | 1.5 | 3 | 4.5 | средний опыт командной разработки |
| E2 | Опыт в предметной области | 0.5 | 3 | 1.5 | с systemd хорошо знаком один участник из четырёх |
| E3 | Опыт объектно-ориентированного подхода | 1 | 3 | 3 | средний |
| E4 | Квалификация ведущего аналитика | 0.5 | 3 | 1.5 | средняя |
| E5 | Мотивация | 1 | 4 | 4 | проект выбран самой командой |
| E6 | Стабильность требований | 2 | 4 | 8 | требования ясные, это лучший критерий концепции в фазе 1 |
| E7 | Частичная занятость участников | -1 | 0 | 0 | оценка делается для команды с полной занятостью |
| E8 | Сложность языка программирования | -1 | 2 | -2 | Go, язык средней сложности |
| | Сумма | | | 20.5 | |

ECF = 1.4 - 0.03 × 20.5 = 0.785.

Факторы среды уменьшают оценку на 21.5%: в основном за счёт стабильных требований и мотивации.

## 5. Результат

UCP = UUCP × TCF × ECF = 145 × 1.015 × 0.785 = 115.5.

Число часов на один UCP выбрано по правилу Шнайдера и Уинтерса. Считается, сколько факторов среды неблагоприятны: сколько из E1-E6 оценены ниже 3 и сколько из E7-E8 выше 3. Если таких факторов не больше двух, берётся 20 часов на UCP (исходное значение Карнера), если три или четыре - 28 часов, если больше - проект считается слишком рискованным. У нас неблагоприятных факторов нет, поэтому берётся 20 часов.

| Показатель | Значение |
|------------|----------|
| UAW | 10 |
| UUCW | 135 |
| UUCP | 145 |
| TCF | 1.015 |
| ECF | 0.785 |
| UCP | 115.5 |
| Часов на 1 UCP | 20 |
| Трудозатраты | 2311 чел.-ч |
| | 289 чел.-дней (по 8 ч) |
| | 14.4 чел.-месяца (по 160 ч) |

Если распределить трудозатраты по use cases пропорционально их весу, на средний use case приходится около 171 ч, на сложный - около 257 ч.

## Анализ

- Оценку почти полностью определяют use cases: UUCW даёт 135 из 145 невыровненных UCP, акторы - только 10.
- Метод грубо различает use cases: все они попали в два класса из трёх, и девять из двенадцати получили одинаковый вес 10. UC8 с четырьмя шагами весит столько же, сколько UC7 с семью. COSMIC те же use cases различает от 11 до 25 CFP.
- Результат чувствителен к тому, что считать транзакцией. UC7 (7 шагов) находится на границе: с восемью шагами он стал бы сложным, и оценка выросла бы на 80 чел.-ч. Если бы все use cases были сложными, получилось бы 151 UCP и 3028 чел.-ч, на 31% больше.
- Ещё сильнее результат зависит от числа часов на UCP. При 28 часах вместо 20 получается 3235 чел.-ч. Эта величина взята из литературы, а не из опыта команды, поэтому оценку нужно считать ориентировочной.
- Оценка включает весь цикл разработки: анализ, проектирование, программирование, тестирование и управление проектом, а не только написание кода.

Если сопоставить с COSMIC, на 1 CFP приходится 2311 / 215 ≈ 10.7 ч. Сравнение оценок между собой и выводы о масштабе проекта делаются в итоговом пункте фазы.
